# osheep 项目文档

## 一、总述

osheep 是一个 AI 驱动的 **服务器端 Web 开发工作台**，目标是在浏览器中提供接近 VS Code 的项目开发体验，并将 AI 的"需求理解 → 文档生成 → 文档对齐 → Todo 生成 → 执行开发"流程整合进统一工作台中。

osheep 长期部署在服务器上，浏览器只是远程访问入口：
- 用户在浏览器看到的、修改的是**服务器上**的文件，不是本地磁盘
- 所有文件读写、终端进程都跑在后端
- 文件 API 与终端 API 的 schema 设计上同样适合 LLM 工具调用——AI 与人类用户共享同一组接口

当前阶段聚焦以下两类能力：

1. Web IDE 基础能力
   - 浏览器中选择 / 打开服务器上的工作区
   - 浏览文件树（通过文件 API）
   - 编辑代码与文档（通过文件 API）
   - 集成的服务器端终端（xterm.js + 后端 node-pty）
   - 拥有基础自动补全能力

2. AI 生成能力
   - 用户输入需求
   - AI 生成项目文档
   - 用户通过多轮对话和手动编辑文档与 AI 达成一致
   - 用户批准后 AI 生成 Todo
   - 用户批准后 AI 开始执行开发任务

当前 MVP 不包含"维护"能力的完整实现。代码审查、Issue/PR 审查等维护功能将在后续阶段设计和接入。

## 二、`.osheep` 目录结构

`.osheep` 是 osheep 在每个 **服务器端工作区** 根目录下创建的工作区子目录，用于存放该 workspace 的设置、计划和文档：

```
.osheep/
├── settings.json        项目级设置（字号、缩进、AI Provider、执行策略等）
├── agent/               用户自定义 Agent，单个文件 `[名称].json`
├── session/             AI 对话会话，单个文件 `[id].json`
├── plan/                阶段计划、版本计划、实现计划（顶层独立目录，便于快速访问）
└── docs/                项目所有其它文档
    ├── README.md        本索引文件
    ├── product/         产品定位、目标用户、核心流程、产品边界
    ├── frontend/        前端工作台、布局、交互流程、编辑器设计
    ├── backend/         后端接口、任务调度、工作区管理、服务边界
    ├── ai/              AI 工作流、提示词职责、Provider 抽象
    ├── data/            核心数据模型、状态流转、对象定义
    └── infra/           部署、运行时、容器、资源控制
```

### 2.1 `.osheep` 根文件规则

- `settings.json`
  - 当前项目的 osheep 设置文件
  - 由 osheep 在打开项目时自动创建（缺失则写入默认值）
  - 保存前端设置、AI 行为设置、Provider 设置、执行策略等项目级配置

- `plan/`
  - **顶层目录**，与 `docs/` 平级
  - 存放阶段计划、版本计划、实现计划
  - 工作台底部面板的"计划"视图直接读取此目录并渲染为只读 Markdown 预览
  - 文件命名规则：`序号-主题.md`，例如 `0001-mvp-web-ide-and-generate-flow.md`

- `agent/`
  - **顶层目录**，与 `docs/`、`plan/` 平级
  - 存放用户自定义 Agent 配置，单个文件 `[Agent 名称].json`
  - 由 Agent 管理页面（活动栏底部机器人图标）写入与维护
  - 每个文件结构见 `docs/frontend/agent-page.md`

- `session/`
  - **顶层目录**，与 `agent/`、`plan/`、`docs/` 平级
  - 存放 AI 对话会话，单个文件 `[id].json`
  - 由工作台右侧 AI 面板的「编写」栏维护
  - 每个文件结构见 `docs/frontend/ai-panel.md` 与 `docs/backend/session-api.md`

- `docs/`
  - 除计划之外的所有项目文档统一存放位置
  - osheep 打开任意项目时若不存在则自动创建
  - 子目录划分见下方 2.2

### 2.2 `docs/` 子目录规则

- `product/`
  - 存放产品定位、目标用户、核心流程、产品边界等文档
  - 文件命名规则：使用功能主题命名
  - 例如：`user-workflow.md`

- `frontend/`
  - 存放前端工作台、布局、交互流程、页面结构、编辑器相关设计
  - 文件命名规则：使用具体功能命名
  - 例如：`document-panel.md`

- `backend/`
  - 存放后端接口、任务调度、工作区管理、服务边界相关设计
  - 文件命名规则：使用具体能力命名
  - 例如：`task-orchestration.md`

- `ai/`
  - 存放 AI 的工作流、提示词职责、文档生成逻辑、Todo 生成逻辑、Provider 抽象设计
  - 文件命名规则：使用 AI 能力命名
  - 例如：`document-generation.md`

- `data/`
  - 存放核心数据模型、状态流转、对象定义
  - 文件命名规则：使用领域主题命名
  - 例如：`domain-model.md`

- `infra/`
  - 存放部署、运行时、容器、资源控制等基础设施设计
  - 文件命名规则：使用运行能力命名
  - 例如：`deployment-runtime.md`

### 2.3 文件命名规则

- 文件名统一使用小写英文
- 单词之间使用 `-` 分隔
- 文件名必须表达单一主题
- 一个文件尽量只描述一个能力或一个边界
- 不使用 `final`、`new`、`temp`、`最新版` 等无语义命名

### 2.4 文档编写规则

- 优先写"目标、边界、输入、输出、约束"
- 先定义行为，再定义实现
- 先定义用户流程，再定义技术方案
- 避免在产品文档中混入过多实现细节
- 避免在实现文档中重新发明产品目标
- 当需求变更时，优先更新已有文档，而不是新增重复文档

## 三、需要的环境

### 3.1 前端环境
- Node.js 20+
- TypeScript
- React
- Monaco Editor（通过 `@monaco-editor/react`）
- xterm.js（终端渲染）
- marked + DOMPurify（Markdown 预览）

### 3.2 后端环境
- Node.js 20+
- TypeScript
- Fastify（HTTP + WebSocket）
- node-pty（终端 PTY）
- PostgreSQL 15+（任务编排，后续阶段）
- Redis 7+（BullMQ 队列，后续阶段）
- BullMQ（后续阶段）

### 3.3 执行与隔离环境
- Docker
- Linux 服务器优先
- 支持长期运行的后台进程管理工具
- 未来可扩展容器化工作区执行环境

### 3.4 AI 接入环境
- 可插拔 LLM Provider
- 支持至少一个主力模型供应商
- 支持流式输出
- 支持后续扩展为多 Provider 切换

## 四、当前阶段范围

当前阶段只做以下内容：

1. Web IDE 基础工作台
2. 需求到文档生成的 AI 流程
3. 文档确认后的 Todo 生成流程
4. Todo 确认后的执行入口与任务状态展示
5. 项目文档统一存放在 `.osheep/docs/`，项目计划存放在 `.osheep/plan/`

当前阶段不做以下内容：

1. PR 审查
2. Issue 审查
3. 自动代码维护模式
4. 多人协同编辑
5. 复杂权限系统

---

## 五、当前协作原则

1. 用户需求必须先沉淀为文档
2. 文档未批准前不得直接进入代码执行
3. Todo 未批准前不得自动执行开发
4. 所有阶段都应可回看、可修改、可重新生成
5. AI 输出必须尽量结构化，便于前端展示和人工修订
